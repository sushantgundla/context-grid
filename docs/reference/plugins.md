# Plugin catalogue

Every plugin registered on every axis, as `context-grid` actually sees them — generated by
running the registries, not typed by hand. If a name isn't here, it isn't installed or it
doesn't exist; `contextgrid plugins` prints the same list for whatever's installed in your
own environment.

For what each axis *is* — the concept, the trade-offs, when to sweep it — see
[the dimension pages](../dimensions/). This page is the flat reference: name, spec string,
one line, and the extra you need. For what an extra installs, see [install.md](install.md).

## How to read a spec string

A spec string is a plugin name, optionally followed by parameters:

```
"recursive"                 -> defaults
"recursive:512"             -> the plugin's shorthand parameter (size=512 here)
"recursive:512,overlap=64"  -> shorthand plus keywords
"recursive:overlap=64"      -> keywords alone, no shorthand
```

Only the *first* bare value (no `=`) is allowed, and only if the plugin declares a shorthand.
Everything else must be `key=value`. This is what a config's `chunker: recursive:512` or a
CLI's `--chunker recursive:512` resolves through — see
[configuration.md](../guide/configuration.md).

## Regenerating this page

```bash
.venv/bin/python -c "
from contextgrid.parse import PARSERS
from contextgrid.ingest import INGESTERS
from contextgrid.chunk import CHUNKERS
from contextgrid.embed import EMBEDDERS
from contextgrid.index import INDEXES
from contextgrid.transform import TRANSFORMS
from contextgrid.retrieve import RETRIEVERS
from contextgrid.rerank import RERANKERS
from contextgrid.evalset import LLMS
from contextgrid.tokens import TOKENIZERS

for family, reg in {
    'parse': PARSERS, 'ingest': INGESTERS, 'chunk': CHUNKERS, 'embed': EMBEDDERS,
    'index': INDEXES, 'transform': TRANSFORMS, 'retrieve': RETRIEVERS,
    'rerank': RERANKERS, 'evalset (llm)': LLMS, 'tokenizer': TOKENIZERS,
}.items():
    print(f'=== {family} ===')
    for r in sorted(reg, key=lambda x: x.name):
        print(r.name, r.extra, r.package, r.shorthand, r.doc)
"
```

Or, from the CLI: `contextgrid plugins` — it prints exactly what's installed in your own
environment, which may be a subset of this page if you haven't installed every extra.

## `parser`

Reads a source file into text. See [parsers](../dimensions/parsers.md).

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `text` | `text` | Plain text, split into paragraphs. No dependencies. | — |
| `markdown` | `markdown` | Markdown with headings, code, lists and tables. No dependencies. | — |
| `pymupdf` | `pymupdf` | Fast PDF text extraction. The speed baseline. | `parse` (`pymupdf`) |
| `pdfplumber` | `pdfplumber` | Table-aware PDF extraction. | `parse` (`pdfplumber`) |
| `pymupdf4llm` | `pymupdf4llm` | Markdown from the PyMuPDF engine. Tests output format, not extraction. | `parse` (`pymupdf4llm`) |
| `docling` | `docling` | Layout and table-structure models. PDF, DOCX, PPTX, HTML. The table arm. | `parse-ml` (`docling`) |
| `marker` | `marker:<languages>` | Surya layout and OCR, 90+ languages. The most faithful and by far the slowest. | `parse-marker` (`marker-pdf`) |
| `agno` | `agno:<reader>` | Text through agno's readers. What most RAG stacks use without choosing to. | `agent` (`agno`) |

**`marker` moved out of `parse-ml` into its own `parse-marker` extra.** `marker-pdf` and
`docling` can't share an environment: `marker-pdf` wants `transformers>=5.12`/`pillow<11`,
`docling` wants `transformers<5.9`, and `pdfplumber` (from `parse`) wants `pillow>=12.2`. pip
resolves all three onto some set by backtracking, and the set it lands on installs cleanly
and then breaks `docling` at runtime with `ConversionError: KeyError: torch.float64` — a
resolver saying yes isn't the same as the combination working. Install `marker` on its own
(`pip install "context-grid[parse-marker]"`) when the `marker` arm is what you're measuring;
don't mix it into the same environment as `docling`. See [install.md](install.md) for the
full extras table.

**A stale error message from before that split:** the registration above correctly says
`parse-marker`, but `MarkerParser`'s own import failure, in `src/contextgrid/parse/layout.py`
(line 273), still raises `MissingExtraError("The marker parser", "parse-ml",
package="marker-pdf")` — the wrong extra, since `marker-pdf` is no longer in `parse-ml` at
all. If you see that message, install `context-grid[parse-marker]`, not `[parse-ml]`.

**`unstructured` has been removed.** It was registered under `parse-ml` but the module
backing it was never written — asking for it raised `MissingExtraError` naming `parse-ml`,
which doesn't contain the `unstructured` package and wouldn't have helped anyway. Advertising
a plugin that cannot run is the same failure as a config key nobody reads; see the module
docstring in `src/contextgrid/parse/__init__.py`. The parser axis is now eight names, not
nine: `agno`, `docling`, `markdown`, `marker`, `pdfplumber`, `pymupdf`, `pymupdf4llm`, `text`.

## `ingestion`

What goes into the index, and what a hit on it returns to the caller — see
[ingestion](../dimensions/ingestion.md). `null` (the config default) means plain chunking,
where those two things are the same.

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `plain` | `plain` | Index the chunk, return the chunk. The baseline. | — |
| `parent-document` | `parent-document:<group>` | Index small chunks, return the passage they came from. | — |
| `sentence-window` | `sentence-window:<window>` | Index one chunk, return it with its neighbours either side. | — |
| `hierarchical` | `hierarchical:<group>` | Index leaves; return the parent once enough siblings hit. Decides at query time. | — |
| `contextual` | `contextual:<model>` | Prepend an LLM-written note on where the chunk sits, and index that. | needs a model — see [`run.model`](../guide/configuration.md#run--how-the-sweep-executes), package via `llm` |
| `propositions` | `propositions:<count>` | Index atomic facts; return the chunk they came from. | — |
| `hypothetical-questions` | `hypothetical-questions:<count>` | Index the questions a chunk answers; return the chunk. | — |
| `summary` | `summary:<model>` | Index a summary of each document; return the document. One call per document. | needs a model, package via `llm` |

`contextual` and `summary` aren't in the extras system the way `parse-ml` or `agent` are —
their `extra`/`package` fields are unset because what they need isn't a pip package, it's an
LLM you configure via `run.model`. See [cost.md](cost.md) for how that gets priced.

## `chunker`

Cuts text into pieces — see [chunkers](../dimensions/chunkers.md).

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `fixed` | `fixed:<size>` | Fixed-size token windows with overlap. | — |
| `recursive` | `recursive:<size>` | Split on the largest separator that fits. The default. | — |
| `sentence` | `sentence:<window>` | A sliding window of whole sentences. | — |
| `semantic` | `semantic:<percentile>` | Cut where consecutive sentences change topic. | — |
| `structural` | `structural:<max_size>` | One chunk per section, bounded by size. | — |
| `chonkie:recursive` | `chonkie:recursive:<size>` | Chonkie's recursive splitter. The head-to-head against ours. | `chunk` (`chonkie`) |
| `chonkie:sentence` | `chonkie:sentence:<size>` | Whole sentences, chonkie's. | `chunk` (`chonkie`) |
| `chonkie:token` | `chonkie:token:<size>` | Fixed token windows, chonkie's. | `chunk` (`chonkie`) |
| `chonkie:code` | `chonkie:code:<size>` | Splits on the syntax tree. Nothing hand-written comes close. | `chunk` (`chonkie`) |
| `langchain:recursive` | `langchain:recursive:<size>` | What most deployed systems are actually running. | `chunk` (`langchain-text-splitters`) |
| `langchain:character` | `langchain:character:<size>` | One separator only. The naive baseline. | `chunk` (`langchain-text-splitters`) |
| `langchain:markdown` | `langchain:markdown:<size>` | Recursive, Markdown boundaries first. | `chunk` (`langchain-text-splitters`) |

Every token-measuring chunker takes a `tokenizer:` parameter (default `regex`). It matters
for caching — see [caching.md](caching.md) for why "512" isn't the same chunk set under two
different tokenizers.

## `embedder`

Turns text into vectors — see [embedders](../dimensions/embedders.md).

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `hash` | `hash:<dimensions>` | Hashed bag of words. No model needed. | — |
| `tfidf` | `tfidf:<max_features>` | Classical TF-IDF over the corpus vocabulary. | — |
| `length` | `length` | Text length in one dimension. A chance-level control. | — |
| `tei` | `tei:<model>` | A local text-embeddings-inference server. No key, no network, no extra dependency. | — (needs a running TEI server, no package) |
| `litellm` | `litellm:<model>` | Any hosted model, through litellm. Bring your own key. | `llm` (`litellm`) |

`null` is also valid here (config default `tfidf`) — it means no embedder, which is what a
`bm25` index wants.

## `index`

How the search actually happens — see [indexes](../dimensions/indexes.md).

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `dense` | `dense:<metric>` | Exact dense search. The reference arm. | — |
| `bm25` | `bm25:<k1>` | Okapi BM25. No model, no vectors. | — |
| `hybrid` | `hybrid:<fusion>` | Dense plus BM25, fused by rank or score. | — |
| `quantized` | `quantized:<scheme>` | Compressed dense search: scalar, product or binary, with optional rescoring. | — |
| `faiss` | `faiss:<kind>` | faiss: flat, hnsw, ivf or ivfpq. Four index types on one axis. | `index` (`faiss`) |
| `usearch` | `usearch:<dtype>` | usearch HNSW, with f32/f16/i8 storage. A second opinion on the same idea. | `index` (`usearch`) |
| `pgvector` | `pgvector:<kind>` | Postgres with pgvector: exact, hnsw or ivfflat. What people actually deploy on. | `pgvector` (`psycopg`), plus a running Postgres |

`usearch`'s valid `dtype`s are `f32`, `f16`, `i8` (`UsearchIndex.DTYPES` in
`src/contextgrid/index/ann.py`) — `b1` was tried and deliberately dropped. usearch's binary
mode wants bit-packed input and a Hamming metric, not the float vectors every other value on
this axis takes; registering `b1` as a dtype raised `ValueError: The number of vector
dimensions doesn't match!` on the first build. Binary quantization still works properly on
this package's own terms: `quantized:binary` does it with a rescoring pass to recover the
recall it costs, see the `index` row above.

## `transform`

Rewrites the question before searching with it — see [transforms](../dimensions/transforms.md).

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `none` | `none` | Search with the question as asked. The arm to beat. | — |
| `expand` | `expand` | Spell out acronyms. Free, and it moves BM25 more than most of the rest. | — |
| `hyde` | `hyde` | Search with a hypothetical *answer* rather than the question. | needs a model, package via `llm` |
| `multi-query` | `multi-query:<n>` | Ask the same thing several ways and fuse the results (default 3 variants). | needs a model, package via `llm` |
| `decompose` | `decompose:<n>` | Break a multi-part question into sub-questions and search each (default 3). | needs a model, package via `llm` |
| `step-back` | `step-back` | Ask the more general question alongside the specific one. | needs a model, package via `llm` |

**`hyde`, `multi-query`, `decompose` and `step-back` are deliberately not in the
`TRANSFORMS` registry.** A transform built from a bare spec string with no model would
silently become the identity transform, and a config that looks like it's testing HyDE while
testing nothing is worse than a hard error. So these four live in
`contextgrid.transform.MODEL_BACKED` and are built by `get_transform(spec, llm=...)` once a
model is available — `contextgrid.transform.available_transforms()` is the complete list of
six, registry plus model-backed, and is what `contextgrid plugins` and the config template
actually print. Only `none` and `expand` show up in a plain registry dump.

## `retrieval`

How the index is queried, as opposed to what it is — see
[retrieval](../dimensions/retrieval.md).

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `simple` | `simple` | One search per query. The arm every other strategy has to beat. | — |
| `widened` | `widened:<factor>` | Search deeper than asked, then cut back. No model calls. | — |
| `decomposed` | `decomposed:<max_parts>` | Split a multi-part question and search each. Mechanical, so it costs nothing. | — |
| `agentic` | `agentic:<model>` | A model plans the searches, optionally over several rounds. Costs a call per query. | needs a model, package via `llm`; benefits from `agent` (`agno`) |

|---|---|---|---|
| `none` | `none` | Keep the retriever's order. The arm every reranker must beat. | — |
| `lexical` | `lexical:<length_penalty>` | Query-term coverage. Free, and the floor. | — |

## Model (LLM), for `run.model` and the generation judge

Not a grid axis — one model backs every strategy above that needs one (the model-backed
transforms, `agentic` retrieval, `contextual`/`summary` ingestion, and the DeepEval judge),
set once via `run.model` in the config. See [cost.md](cost.md) for how it's priced.

| Name | Spec string | Description | Extra |
|---|---|---|---|
| `litellm` | `litellm:<model>` | Any chat model through litellm. Bring your own key. | needs `litellm` installed, but registered in-tree — see note below |
| `openai` | `openai:<model>` | OpenAI chat, through litellm. | same |
| `anthropic` | `anthropic:<model>` | Anthropic messages, through litellm. | same |

These three show `extra=None` in a raw registry dump — unlike the lazily-registered plugins
above, they're registered as ordinary in-tree factories (`LLMS.register(...)`), and the
`litellm` import happens inside `LiteLLMChat` itself, raising `MissingExtraError("Model
calls", "llm", package="litellm")` on first use if it's missing. Functionally they still need
the `llm` extra; the registry just doesn't know that about them the way it does for, say,
`docling`.

## A registration nobody sweeps: the tokenizer

Chunkers that measure size in tokens take a `tokenizer:` parameter, itself a small registry
(`contextgrid.tokens.TOKENIZERS`), not a grid axis:

| Name | Description | Extra |
|---|---|---|
| `regex` | Words and punctuation by regex. No dependencies. Not exact — do not use to price anything. | — |
| `character` | One token per character. Exact and unit-free. | — |
| `cl100k_base` | OpenAI's `cl100k_base`, via `tiktoken`. Exact, so the cost model will price with it. | `embed` (`tiktoken`) |
| `o200k_base` | GPT-4o's encoding, via `tiktoken`. Exact. | `embed` (`tiktoken`) |

Both real-model tokenizers now work — this was fixed after an earlier pass of this page
flagged `cl100k_base` as broken. It was worse than a missing extra: the registration pointed
at a module, `contextgrid.tokenizers_tiktoken`, that had never been written. So asking for
`cl100k_base` raised an install instruction (`pip install "context-grid[embed]"`) for an
extra that also didn't exist, and even installing `tiktoken` by hand wouldn't have found the
module. Both gaps are closed: `pyproject.toml` now has an `embed = ["tiktoken>=0.7"]` extra,
and `src/contextgrid/tokenizers_tiktoken.py` implements `TiktokenTokenizer` against the full
`Tokenizer` protocol — including `token_spans`, real character offsets rather than just a
count, which is what lets a chunker actually cut on a model's real token boundaries instead
of guessing. Verified end to end, spans included:

```
$ .venv/bin/python -c "
from contextgrid.tokens import get_tokenizer
text = 'Hello, world! 日本語のテスト 🎉'
for name in ['cl100k_base', 'o200k_base']:
    tok = get_tokenizer(name)
    spans = tok.token_spans(text)
    print(name, 'exact=', tok.exact, 'count=', tok.count(text))
    print(' reconstructs exactly:', ''.join(text[a:b] for a, b in spans) == text)
"
cl100k_base exact= True count= 14
 reconstructs exactly: True
o200k_base exact= True count= 11
 reconstructs exactly: True
```

The `embed` extra is real now (see [install.md](install.md)): counted among the axis extras,
there are 9 of them, not 8.
